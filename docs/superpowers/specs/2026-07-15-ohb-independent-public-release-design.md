# OHB 独立公开产品发布设计

## 1. 目标

将 One Holy Bible 落成两个物理独立、运行独立、Git 历史独立的版本：

- 完整开发版：`/Users/simon/OHB/one-holy-bible`
- GitHub 公开版：`/Users/simon/OHB/one-holy-bible-github`

开发版是唯一功能开发源和公开内容导出源。GitHub 版是经过白名单选择、字段清洗和完整校验后产生的只读公开产品。两个版本之间只允许“开发版到 GitHub 版”的单向发布，不允许反向同步或整目录互拷。

公开产品保留：

- CUV/KJV 阅读与检索；
- 66 卷导航；
- 解释文字卡；
- 用户明确允许公开的图片卡；
- 阅读布局和图片预览等纯前端功能。

公开产品排除：

- `Edit` 卡片工作台和编辑 API；
- 本机地址、绝对路径和源文件路径；
- 工作台卡片 ID、内部审核状态和同步状态；
- 原始文档、提取中间产物和未纳入公开范围的数据；
- 任何需要 `127.0.0.1:5127` 或 `127.0.0.1:5179` 才能运行的功能。

## 2. 非目标

- 不把两个版本改成同一 Git 仓库的两个分支。
- 不把 3GB 以上图片资源直接提交到普通 Git 历史。
- 不允许在 GitHub 公开版中独立演化一套无法回流开发源的公共功能。
- 不在本设计中绑定某一家对象存储或静态托管供应商。
- 不自动推送未经本地验证和发布差异检查的内容。

## 3. 当前状态与主要问题

当前工作区已有两个独立 Git 仓库，但发布接口尚未工程化：

- 开发版约 8.4GB，包含完整应用、约 3GB `public/resources`、约 240MB `src/data/generated`，并连接本地卡片工作台数据链。
- GitHub 版约 292MB，公开数据约 51MB，当前为文字优先 `v0.1.0`，远端 `origin/main` 和 CI 正常。
- 两个目录有 141 个同路径文件，其中 23 个已经内容不同；手工复制无法可靠维护。
- 开发仓库仍包含上一轮公开版历史和脚本痕迹，GitHub 公开版没有开发源提交与内容输入哈希的发布记录。
- 图片资产不适合与网站代码一起反复构建和上传。

## 4. 总体架构

```text
Edit + Resources + 文档
          |
          v
one-holy-bible（唯一开发源）
          |
          | 代码白名单 + 公共数据生成 + 隐私清洗 + 资源清单生成
          v
临时发布区（每次全新生成，验证后删除）
          |                         |
          |                         +--> 公开图片资源存储
          v
one-holy-bible-github（独立公开仓库）
          |
          v
GitHub Actions --> Web 部署
```

独立性定义：

- 开发版可以在没有 GitHub 版目录的情况下继续开发和运行。
- GitHub 版可以在没有 `Edit`、`Resources` 和开发版目录的机器上执行 `npm ci`、测试、构建和运行。
- GitHub 版不得通过软链接、绝对路径、父目录导入或运行时本地 API 访问开发版。
- GitHub 版的每次变更必须能追溯到开发代码提交和内容输入哈希。

## 5. 代码所有权与目录边界

### 5.1 开发版是唯一源头

公共功能首先在开发版实现。开发版代码逐步划分为：

```text
src/core/                 阅读器、工作台纯 UI、领域模型和通用工具
src/development/          完整开发入口、本地工作台同步和编辑能力
src/public/               公开只读入口、公开数据适配器
release/public-template/  GitHub 元数据、公开说明、CI 和构建模板
scripts/release/          单向发布器、校验器和发布清单生成器
```

现有代码不要求一次性全部迁移。首轮只移动发布边界必须涉及的入口和数据适配器；大型 `Workbench.tsx` 的无关重构不进入本次范围。

### 5.2 GitHub 版是派生产物

GitHub 版包含：

```text
src/core/                 从指定开发提交导出的共享代码
src/public/               从指定开发提交导出的公开入口
src/main.tsx              公开入口启动文件
public/data/              按书卷生成的公开数据
scripts/validate/         只读公开校验工具
.github/workflows/        CI 和部署工作流
README.md 等              公开说明和许可文件
```

GitHub 版原则上不直接开发。紧急公开版修复必须先在开发版修复并测试，再重新发布。GitHub 版只保留其自身 Git 历史、发布标签和部署状态。

### 5.3 发布器采用白名单

发布器维护明确的源路径到目标路径映射。未列入映射的内容一律不进入临时发布区。禁止使用以下方式：

- `cp -R` 整个开发仓库；
- 对 GitHub 仓库根目录直接执行不受限的 `rsync --delete`；
- 从开发版创建 Git worktree 充当公开版；
- 在开发版中临时改写 `App.tsx` 或默认构建配置进入“公开模式”。

## 6. 公开数据契约

公开数据升级为可容纳文字卡和图片卡的 schema v2，并继续按书卷拆分。

每卷数据包包含：

```json
{
  "schemaVersion": 2,
  "bookId": "Gen",
  "cuvVerses": [],
  "kjvVerses": [],
  "textCards": [],
  "imageCards": []
}
```

公开文字卡允许字段：

- `id`
- `type`（仅 `commentary` 或 `note`）
- `title`
- `body`
- `verses`
- `primaryAnchor`
- `bookIntro`
- `summary`
- `searchText`
- 经过清洗的 `sourceLabel`、页码和经文覆盖范围

公开图片卡允许字段：

- `id`
- `type`（固定为 `image`）
- `title`
- `body`
- `verses`
- `primaryAnchor`
- `bookIntro`
- `summary`
- `sourceLabel`
- `asset.url`
- `asset.sha256`
- `asset.bytes`
- `asset.mimeType`
- `asset.width`
- `asset.height`

公开图片卡不得包含：

- `assetPath`
- `/Users/...`、`/Volumes/...` 或 Windows 绝对路径
- `sourceAssetPath`
- `storedAbsolutePath`
- `sourcePdfPath`
- `sourceWorkbenchPath`
- `sourceWorkbenchCardId`
- `sourceApiBase`
- `reviewStatus`、`syncStatus`、风险审核字段

公开运行时适配器把 `asset.url` 转换为 UI 使用的只读图片地址，不重新引入本地路径字段。

## 7. 图片资源契约

实际图片文件独立于 GitHub 代码仓库保存。资源层不是第三个应用版本，而是公开版依赖的不可变静态资产层。

资源对象使用内容寻址：

```text
ohb-assets/<sha256>.<extension>
```

规则：

- 相同内容只上传一次。
- 图片更新产生新哈希和新 URL，不覆盖旧对象。
- 每次发布先上传缺失图片，再发布引用这些图片的代码和清单。
- 已发布旧 URL 保持可访问，以保证旧版本可回滚。
- 图片上传后校验字节数、SHA256、MIME 类型和可访问性。
- 发布器只上传新增或变化的图片，不重复传输全部图片库。

对象存储供应商通过适配器配置，公开数据契约不依赖具体供应商。首次实施可以先提供本地文件系统适配器完成全链路演练，再接入正式存储。

## 8. 发布清单

GitHub 版根目录生成 `PUBLIC_RELEASE.json`，至少包含：

```json
{
  "releaseVersion": "0.2.0",
  "schemaVersion": 2,
  "developmentSourceCommit": "<40-character SHA>",
  "bibleInputSha256": "<sha256>",
  "cardInputSha256": "<sha256>",
  "assetManifestSha256": "<sha256>",
  "bookCount": 66,
  "cuvVerseCount": 31102,
  "kjvVerseCount": 31102,
  "textCardCount": 0,
  "imageCardCount": 0,
  "generatedAt": "<ISO-8601>"
}
```

计数由生成器写入，禁止人工修改。GitHub 提交信息和发布标签同时记录 `developmentSourceCommit`。

## 9. 单向发布流程

### 9.1 准备阶段

命令形态：

```bash
npm run release:prepare -- --version 0.2.0 --source <development-commit>
```

流程：

1. 确认 GitHub 版目录存在、位于预期路径、`origin` 指向预期仓库且工作区干净。
2. 确认开发源提交存在。代码只从该提交导出，不读取未提交代码改动。
3. 内容输入允许位于 Git 之外，但必须在开始时锁定路径、大小、修改时间和 SHA256；生成结束后再次核对，防止发布过程中变化。
4. 在系统临时目录创建全新的发布区，不修改两个正式仓库。
5. 根据白名单导出共享代码、公开入口、模板和许可文件。
6. 清洗并生成 66 卷公开数据、搜索索引、图片资源清单和 `PUBLIC_RELEASE.json`。
7. 通过资源适配器检查或上传缺失图片。
8. 在临时发布区执行隐私扫描、数据校验、单元测试、类型检查和生产构建。
9. 输出与当前 GitHub 版的文件、数据计数和体积差异报告。

准备阶段任何一步失败，删除临时发布区并保持两个正式仓库不变。

### 9.2 发布阶段

命令形态：

```bash
npm run release:publish -- --version 0.2.0
```

流程：

1. 校验准备结果未过期，输入哈希和 GitHub 当前 HEAD 未发生变化。
2. 再次确认 GitHub 版工作区干净。
3. 把临时发布区的受管文件同步到 GitHub 版；保留 `.git`，不读取开发版工作区文件。
4. 在 GitHub 版重新执行公开数据校验、测试、类型检查和构建。
5. 创建单一发布提交和带注释标签。
6. 推送 `main` 和发布标签。
7. 等待 CI/部署结果并执行线上冒烟检查。
8. 成功后删除临时发布区；失败则保留差异报告并进入回滚流程。

用户说“同步到 GitHub”时，默认执行这套独立公开版流程。若未提供版本号，发布器只准备并报告建议版本，不自行猜测正式标签。

## 10. 原子性、失败处理与回滚

- GitHub 版不干净：立即停止，不自动 stash、reset 或覆盖。
- 开发代码未提交：只允许选择已有提交；未提交代码不进入发布。
- 内容输入变化：立即停止并重新计算发布。
- 隐私字段或本机地址命中：立即停止并报告字段位置，不自动忽略。
- 图片缺失或哈希不符：立即停止，不生成引用失效图片的公开提交。
- 测试或构建失败：临时发布区保留诊断报告，正式 GitHub 版保持不变。
- 推送失败：本地发布提交保留，不强推；修复远端状态后重新验证。
- 部署失败：回滚到上一个公开标签；内容寻址图片无需删除。

发布器不得执行 `git reset --hard`、未经确认的强推或对开发仓库的自动提交。

## 11. 安全与隐私校验

发布校验必须覆盖：

- `/Users/`、`/Volumes/`、`file://` 和 Windows 绝对路径；
- `localhost`、内网 IP 和本地服务端口；
- 工作台内部字段和源数据文件名；
- `.env`、密钥、令牌和常见凭证模式；
- 软链接、越界路径和输出目录重叠；
- 单文件大小上限、仓库总大小预算和构建产物大小预算；
- 公开数据精确字段白名单；
- 公开图片 URL、哈希、尺寸和 MIME 类型。

所有校验采用 fail-closed：遇到未知字段或未知资源类型默认拒绝。

## 12. 测试与验证

### 自动测试

- 代码白名单映射测试；
- 文字卡和图片卡清洗测试；
- 隐私字段拒绝测试；
- 66 卷分包、计数、哈希和搜索索引一致性测试；
- 内容输入在生成中变化的失败测试；
- GitHub 版工作区不干净的失败测试；
- 原子发布与失败不修改正式目录的集成测试；
- 图片增量上传和重复内容跳过测试；
- GitHub 公开版全量测试、类型检查和构建。

### 人工验证

- 开发版主路径：完整经文、图片卡、卡片工作台刷新和编辑仍可用。
- 公开版主路径：跨书卷阅读、解释卡、图片加载和图片预览可用。
- 公开版失败路径：书卷数据或图片加载失败时保留当前内容并提供可理解的重试状态。
- 对本次演练产生的控制台、网络、构建和发布日志进行分析，确认没有私有路径、异常时序或静默失败。

## 13. CI 与部署

GitHub Actions 在每次公开提交上执行：

1. `npm ci`
2. 公开数据与隐私校验
3. 单元测试
4. TypeScript 检查
5. 生产构建
6. `PUBLIC_RELEASE.json` 与标签一致性检查
7. 部署或生成可供部署系统使用的构建产物

实际图片不打入 Web 构建目录。部署只更新代码、JSON 清单和搜索索引，因此大多数发布不需要重新传输完整图片库。

## 14. 首次迁移顺序

1. 备份将要修改的开发版和 GitHub 版文件，备份进入 `/Users/simon/备份/codex` 的独立子目录并附说明。
2. 梳理开发仓库现有未提交文件：区分源码、生成物、私有资源和临时文件。
3. 建立可追溯的开发代码基线；不把 3GB 图片和原始文档提交进普通 Git。
4. 建立 `src/core`、`src/development`、`src/public` 的最小入口边界。
5. 实现 schema v2 和图片资源清洗器。
6. 实现临时发布区、白名单导出和 `PUBLIC_RELEASE.json`。
7. 实现本地图片资源适配器和增量清单验证。
8. 在不推送的情况下完成一次 `release:prepare` 全链路演练。
9. 使用本地静态服务人工验证完整开发版和临时公开版。
10. 把生成结果更新到独立 GitHub 版，完成双版本回归测试。
11. 经用户确认后创建首个新架构公开提交、标签并推送。
12. 接入正式图片存储和 Web 部署目标。
13. 删除确认无用的旧 `public-main` 分支和过期公开模式残留；不改写已有历史。

## 15. 验收标准

- 两个正式目录都是独立 Git 工作树，GitHub 版唯一远端仍为预期公开仓库。
- 开发版不再通过切换入口或构建配置进入公开模式。
- GitHub 版在隔离环境中无需开发版、`Edit` 或 `Resources` 即可安装、测试、构建和运行。
- 发布器只从明确开发提交和锁定内容输入生成公开产品。
- GitHub 公开数据包含允许公开的解释卡和图片卡，不包含内部路径或工作台字段。
- 图片资产不进入普通 Git 历史，且第二次无变化发布不会重复上传图片。
- 准备阶段失败不会修改两个正式仓库。
- GitHub 版有完整来源提交、输入哈希、数据计数和资源清单记录。
- 一次正常发布可以通过两阶段命令完成，并能回滚到前一个公开标签。
- 自动测试、生产构建、人工主路径、失败路径和日志分析全部闭环。
